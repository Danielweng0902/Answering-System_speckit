## 發現

### R1｜Low｜換組限制僅由前端強制（001 FR-012／D21），open 中可經 HTTP 取得他組身分
- **對應**：Constitution 原則 VI（不得以前端隱藏代替權限控管）、001 FR-012／D21、003 FR-016／FR-018（C9）邊界。
- **位置**：`server/src/infra/http/authRoutes.ts:129-148`。
- **重現步驟**：活動 open 中，已屬 A 組的學生直接 `POST /api/student/join {"groupId":"<B組id>"}` → 200 回 B 組 token；以該 token 建 Socket.IO 連線即收到 B 組 open 快照（含 B 組 `myAnswers` 已送出答案），並可代 B 組送出。（程式碼路徑確定：join 無任何階段或既有身分檢查，註解明示「Students may join during any activity phase (AC-001-09)」，且 `studentJoin.test.ts` 有「搶答中仍允許進場」測試；我未啟動伺服器實測，runtime 行為標記**推測／待驗證**，但與既有測試一致。）
- **Expected**：D21「學生只能在準備中換組」由伺服器強制。**Actual**：僅 `StudentPage` 在 preparing 顯示「更換組別」（`StudentPage.tsx:112-133`），API 層無限制。
- **評估與建議**：這是設計層規格洞而非單純實作 bug——D3 學生無帳號、無 per-person identity，伺服器無法區分「新進場」與「換組」，任何人本來就能一開始就選 B 組，邊際風險是「同時保有兩組視角」。依憲法原則 I，**應停下回報並做成決策**（例如：接受並在文件記載此限制，或 001 變更為 open 階段 join 需綁定既有 token／限同組）。不建議在 003 branch 單方面改行為（會影響兩組一致性，需 OpenSpec 組同意）。

### R2｜Low（推測／待驗證）｜指令 COMMIT 後的廣播在 try/catch 之外，拋例外時 ack 永不回覆且可能拖垮 process
- **對應**：contracts/socket-events.md「送出 state 後回 { ok: true }」、原則 III（清楚錯誤）。
- **位置**：`server/src/infra/socket/commandRouter.ts:123-141`；`node_modules/socket.io/dist/socket.js:685-698`（`dispatch` 在 `process.nextTick` 中直接 `emitUntyped`，無 try/catch）。
- **重現步驟**：使 `broadcastOnSuccess` 內的 `createSnapshot` 拋例（如 DB I/O 錯誤；正常初始化後不易發生，故標記推測）。**Expected**：學生拿到 `ok:false` 或至少伺服器存活。**Actual**（程式碼推演）：作答已 COMMIT 但 ack 永不送出（前端 10 秒後顯示「伺服器沒有回應」，實際已成功）；例外经 nextTick 成未捕捉例外，可能終止伺服器 process。
- **建議最小修正**：將 `broadcastOnSuccess`/`broadcastState` 呼叫與 `sendAck` 包進 try/catch，捕捉後仍回 ack（資料已 COMMIT，回 `ok:true` 是誠實結果）並只記事件名。`errorHandling.test.ts` 已覆蓋 use case 拋例，可加一個廣播拋例的對照案例。

### R3｜Info（非缺陷）｜answerRepo 讀取路徑為全表掃描＋每筆 N+1 查詢
- **位置**：`server/src/infra/db/answerRepo.ts:25-48`（`readAnswers` 載入全部 submissions 並逐筆查 answers）、`answerCommands.ts:62、108`（每次指令 `listQuestions` 全載）。
- 在規格尺度（≤50 組×數十題×每題≤50 筆）功能正確、僅效能開銷；`findValid` 理論上可改單條 SQL。不需在本分支處理，留給 005 前的整體評估即可。
