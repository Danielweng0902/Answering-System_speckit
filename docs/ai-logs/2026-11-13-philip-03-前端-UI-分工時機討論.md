## 助理

可以，而且不用等後端做完。我看了專案的 `KICKOFF-PLAN.md` 第 4.1 節，計畫裡本來就把**視覺方向、`design/DESIGN.md`、design tokens、線框圖、審每個畫面**分給你。組員那邊則寫「依 `design/` 的規範實作，不自己決定視覺」。所以前端 UI 本來就是你的範圍，只是分工方式是「你決定長什麼樣子，她的 agent 照著寫」。

**現在最該先補的是：`design/DESIGN.md` 還不存在。**`design/` 資料夾裡目前只有 README 和一份參考網站清單。計畫寫明設計要在第一個有畫面的功能進 plan 之前定案，否則 AI 會套預設樣式。你剛看的 5 張截圖就是這個結果：瀏覽器預設的按鈕、灰框、系統字型。001、002 已經這樣做完了，越晚定，之後要改的畫面越多。

**為什麼不用等後端：**前後端之間的「合約」是先寫好的，不是等程式寫完才有。
- **已完成的 001、002：**合約在 `shared/src/protocol.ts`（資料格式、錯誤訊息）和 `specs/00X/contracts/`（HTTP API、socket 事件）。這兩個功能的後端已經好了，你現在就能直接改畫面，完全不必等。
- **還沒做的 003 搶答、004 匯出、005 公平性：**目前只有 `spec.md`，還沒有 contracts。你可以先畫線框圖、定好畫面要顯示哪些資訊。等組員跑到 plan 階段產出 contracts，再接上真正的資料。在那之前可以先用假資料把畫面做出來。

**建議的順序（11/24 功能凍結，大約剩 11 天）：**
1. **寫 `DESIGN.md` 和 tokens：**視覺概念、色票（包含「搶答中」「已送出」「搶答成功」這類狀態色）、繁中字體、間距、禁用清單。計畫裡建議從「黑板／計分板／紙本學習單」找方向。
2. **畫 003 搶答的線框圖：**老師的投影畫面和學生的手機畫面各一張。搶答是整個系統最核心、demo 最顯眼的畫面，要趕在組員 plan 003 之前給她。
3. **套用到 001、002 的現有畫面：**樣式都在 `web/src/features/` 底下，每個元件各有一個 `.module.css`，改樣式不太會動到邏輯。修改時順便處理你剛審出來的 04 重複問題。
4. **用畫面驗收來把關：**每個有畫面的 PR 附截圖，由你對照 `DESIGN.md` 審。

**要事先跟組員說好的一件事：**你是只負責「定規範＋審畫面」，還是也要自己動手寫 `web/` 的程式。如果兩個人（或兩邊的 agent）同時改同一個 `.tsx`，很容易衝突。比較穩的做法是：你另開一個 branch，只改 `.module.css` 和 tokens，不碰元件邏輯；或者約好哪些檔案歸你。

如果你想開始，我可以先根據現有畫面和計畫裡的方向，幫你起草一版 `DESIGN.md`。
