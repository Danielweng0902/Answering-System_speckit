## 一、為什麼現在提：看你們的 spec 就知道時機對了

## 二、我們的提議：重設活動時，**一併作廢該活動所有學生的 session**

### 現況（我們這邊）

| 項目 | 現況 |
|---|---|
| `sessions` 表 | 只有 `token_hash / role / group_id / created_at` —— **沒有到期時間、沒有撤銷旗標** |
| 撤銷 | 只有老師按「登出」時才會撤銷 |
| `activity:reset` | 只清作答資料 ＋ 換 activity 的 session id → **舊的學生 token 照樣有效** |
| 重啟伺服器 | token 存在 SQLite 檔裡 → **重啟後仍有效** |

所以現在「重設活動」之後，上一場的學生 token 仍然可以作答（雖然作答資料已被清空）。
這是語意不一致：**重設 = 清掉這場、重新開始**，但登入狀態留著。

### 提議的行為

重設活動時，把該活動的**學生** session 一併作廢（token 立即失效）。
已連線的學生**不會被踢下線** —— socket 的身分是在連線時解析一次就存著的，每個指令不重查
session 表。受影響的只有「重設之後才連線、或斷線重連」的學生 → 他們會回到選組畫面重新進場。

### 為什麼不是「加到期時間（TTL）」

TTL 會讓學生在**課堂中途**被登出 → 重新進場、重新答卷。一堂課 50 分鐘，TTL 必須大於
一堂課，但逾時邊界怎麼處理（同學分鐘數不同、跨堂重用）是個大坑。我們認為風險比它解決的問題大。

### 為什麼不是「完全不動」

「重設 = 新的一場」這件事在 D19 已經是明文（組別保留、本次活動的作答資料清空）。
但「學生的登入狀態算不算『本次活動的資料』」在條文裡**沒有寫** —— 這就是我們要一起定的地方。

### 實作成本

我們這邊大概 3 行：`sessionRepo.deleteSessionsByRole(database, 'student')` 這個函式**已經存在**
（2026-11-22 D18 時為了「重啟後老師須重新登入」而加的），在 `activity:reset` 的 transaction
裡呼叫即可。你們那邊的 session lifecycle 如果有類似的集中管理，應該也很快。

### 想請你們裁決的

1. **同意**「重設時一併作廢學生 session」嗎？
2. 若不同意，你們那邊對「重設」的語意是什麼？（例如：重設只重置階段與作答，進場狀態保留到 TTL）
3. 同意的話，我們會：改 `activity:reset`、把 D19 與 001 的 FR-022／AC-001-27 補上條文、
   更新對照表，並補學生端的驗收（重設後重新連線的學生回到選組畫面）。

## 三、順便同步三件我們**自己**決定了的事（不用你們介入，但先講一聲）

這三件是資安審計後的待辦，我們逐項讀了程式碼後自己決定了，列出來是為了讓你們知道
**我們刻意不做**，不是忘記了 —— 也順便省你們一輪來回：

| 項目 | 我們的決定 | 依據 |
|---|---|---|
| **答案陣列的長度上限** | **不做** | 實際上有三道防護：Engine.IO 封包上限 1 MB、`answers.length` 與該題空格數的比對、單格 200 code point。先前內部待辦寫的「可以送幾千個空格組合沒有上限」是不準確的，我們已更正 |
| **同時在途的總記憶體上限** | **不做** | 只有認證過的老師能觸發匯入上傳（單檔上限 5 MB），是「自己搞自己」而非外部攻擊。加併發上限要新增錯誤代碼、降單檔上限要動 FR-003 的「不超過 5 MB」，兩者成本都不划算 |
| **合法登入的次數上限** | **不做** | 成功登入是人工操作（不是程式迴圈），成長速率是人類手指的速度；且老師 session 在伺服器重啟時就會被清 |
