## 一、D18 老師身分：兩邊都要密碼，細節對齊 ✅

你們的代碼 `WRONG_PASSWORD`、`TOO_MANY_ATTEMPTS`、`TEACHER_PASSWORD_NOT_SET`、`NO_GROUPS`、
`QUESTIONS_REQUIRED` 我們都對得上。**你們問的未登入代碼：我們改成跟你們一樣的
`TEACHER_AUTH_REQUIRED`（401）**，兩組統一用這個名稱；已登入但不是老師仍然是 403 `FORBIDDEN`。

順帶把三個我們原本跟你們不同、但你們已經有的行為補上（2026-11-22 已實作完成）：

| 項目 | 我們原本 | 現在（與你們一致） |
|---|---|---|
| 登入狀態存放 | sessionStorage（頁面 JS 讀得到） | **HttpOnly cookie**（頁面 JS 讀不到憑證） |
| 登出 | 沒有 | **有**，登出後該登入狀態立即失效 |
| 登入狀態查詢端點 | 沒有 | **有**（回報目前是否已登入、伺服器是否已設定密碼） |
| 伺服器重新啟動 | 老師的登入狀態還有效 | **一律失效，老師須重新登入**（學生的進場狀態不受影響） |

我們的老師端現在多一個「登出」按鈕；登入回應不再把憑證交給頁面 JavaScript。

## 二、D20 組數上限：統一為 100 組 ✅

你們的 64 組實測是關鍵——我們原本照契約寫 50 組，那會直接擋到真的能上課的班級。
**兩組統一為 100 組**，我們這邊已改完（上限、錯誤訊息、測試、壓測工具上限），
契約升 v0.7。

我們也用同一台機器實測了我們自己的 100 組（正式 build、WebSocket、100 組 × 20 題 × 2 輪
＝ 4,000 筆作答；連線 202 條）：

| 指標 | 50 組 | 100 組 |
|---|---:|---:|
| 送出→ACK p50 | 55 ms | **88 ms** |
| 送出→ACK p95 | 90 ms | **158 ms** |
| ACK 逾時率 | 0% | **0%** |
| 必要 state 漏送 | 0 | **0** |
| 錯誤順位 | 0 | **0** |
| 老師看板更新 p95 | 129 ms | **179 ms**（max 416 ms） |
| 穩態 CPU | 31% | **61%** |

情境是「倒數歸零、全班同一秒送出」的最壞情況。量測方法、原始 JSON 與我們為此做的一個
修正（老師看板的廣播合併，見下）都在我們 repo 的
`docs/verification/load-test-2026-11-22-100groups.md`。

**一個我們想跟你們分享的實作心得**：一開始 100 組的冷啟是壞的（ACK p95 撞到 5 秒上限、
逾時 12%、漏送 2,528 筆），原因是「每筆作答都重建並送出整份全場看板」（100 組約 600 KB／份）。
改成「同一個 120 ms 時間窗內只送一份最新看板給老師」之後就正常了，學生端與 ACK 完全不受影響。
你們用 SSE、5,000 筆 0.6～1.1 秒的數字很漂亮，如果之後你們的看板也開始全量推送，
可以留意一下同樣的量級。

順帶一提，我們把部署門檻也調高了（`JOIN_RATE_LIMIT_BURST` 600→1000、`MAX_CONNECTIONS` 500→1000），
因為 100 組班級約 400 人。
