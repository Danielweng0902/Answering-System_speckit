## 一、組別 id：確認，兩邊都不顯示 id ✅

我們也是**用組名顯示**，id 從不顯示在畫面上（學生端、老師端、匯出結果都是組名）。
你們用 1～100 整數、我們用 UUID 字串，**這是內部實作，不影響使用者看到的行為**，就不強求一致。

順便把我們的 CSV 現況給你們（004 已實作、005 加了第 8 欄；D13 早已兩組確認）：

| 欄 | 內容 | 範例 |
|---|---|---|
| 1 題號 | 題目編號 | `1` |
| 2 空格序 | 該題的第幾個空格 | `1` |
| 3 **組別** | **組名**（不是 id） | `第一組` |
| 4 答案 | 該空格的作答文字 | `蘋果` |
| 5 順位 | 該題的送達順位 | `1` |
| 6 是否搶答成功 | 是／否 | `是` |
| 7 送出時間 | **本地時間**（不輸出 UTC `Z` 或時區後綴，v0.4 已確認） | `2026-11-23 09:08` |
| 8 公平順位 | 否／是／是（改判） | `否` |

其他你們可能用得到的：UTF-8 **含 BOM**、CRLF 換行（Excel 直接開不亂碼）；欄位值若以
`= + - @` 開頭會加單引號避免被試算表當成公式；作答內容含逗號／引號／換行時用 RFC 4180
的雙引號轉義。

## 二、cookie：改成跟你們一樣的 Strict ✅

我們原本是 `SameSite=Lax`，現在**改成 `SameSite=Strict`**，跟你們一致：

```
HttpOnly; SameSite=Strict; Path=/        ← 登入（工作階段 cookie，不設 Max-Age）
HttpOnly; SameSite=Strict; Path=/; Max-Age=0   ← 登出時清除
```

不設 `Secure`（課堂區網 HTTP），正式環境走 HTTPS 時再加 —— 這點我們同意。

**一個要提醒的行為差異**（我們兩邊都一樣）：`SameSite=Strict` 代表老師若從**外部網站的
連結**（例如 messenger 的連結）開啟教師頁，cookie 不會跟著帶，畫面會回到登入畫面要重新
輸入密碼。老師在自己開著的分頁或直接輸入區網網址則不受影響。如果你們覺得這在教室裡
會造成困擾，告訴我們，我們再一起討論要不要放寬回 Lax。

契約的 D18 我們把 cookie 屬性**寫進條文**了（v0.8 的變更紀錄），兩邊就此釘住。

## 三、你們老師端「事件帶時間戳、前端自己重查」的做法

你們說每次提交仍會觸發一次查詢 —— 那在我們這邊就是同樣的 N+1 問題，只是我們的 N+1
是發生在**伺服器端**（每次作答重建並推送整份全場看板）。我們的處理是「同一個 120 ms
視窗只送一份最新看板」，你們那邊如果也遇到大量提交時的壓力，可以考慮：

- **伺服器端合併**：同一個短時間窗內的回應合併成一份（我們的做法，改動在伺服器）。
- **前端合併**：前端收到時間戳事件後自己 debounce（例如 100～200 ms 內只查一次），
  改動更小，但每次提交在伺服器端仍會被查一次。

實測數據（我們的 100 組 × 20 題 × 2 輪 = 4,000 筆同時提交）供你們參考：
合併前 ACK p50 1,592.75 ms、逾時 12.15%、漏送 2,528 筆；合併後 ACK p50 87.71 ms、
逾時 0%、漏送 0。你們架構不同，數字不一定適用，但「大量提交時要合併」的結論應該是一樣的。
