## 一、我們發現的缺口（是我們自己的問題，已經修好）

D19（2026-11-25 兩組確認）的內容是：重設會作廢所有學生的進場狀態，**已連線的學生也會被通知並回到選組頁**。

但我們漏了一種情況：**重設當下不在線的學生**（例如手機螢幕關掉、網路不穩）。

- 他們的進場狀態一樣被作廢（token 立即失效）→ 重連後回到選組頁 —— 這部分本來就對，
  與 v0.9 裡寫的「只有重設之後才連線或斷線重連的學生需要重新進場」一致。
- 但**完全沒有通知**：他們的舊 token 查不到 session，伺服器就把他們當一般訪客，
  畫面只是「突然回到選組頁」，學生不知道發生什麼事；瀏覽器裡的舊 token 也留著沒清掉。

我們 reviewer 的原話是：「學生只會突然回到選組頁，不知道發生什麼事（例如手機螢幕關掉或網路不穩時剛好重設）」。

## 二、我們的修法（已實作，在 PR #44）

| 項目 | 內容 |
|---|---|
| 伺服器 | 學生帶著**已失效的 token** 重新連線時，除了訪客快照，也送 `session:invalid`；原因代碼新增 `SESSION_EXPIRED` |
| 學生端 | 收到通知 → 清除瀏覽器裡的舊 token → 回到選組頁並顯示原因「進場狀態已失效，請重新選擇組別」 |
| 已連線的學生 | **不變**：重設當下立刻收到 `ACTIVITY_RESET` → 顯示「活動已重設，請重新選擇組別」 |
| 老師 | 不受影響（老師的登入狀態走 HttpOnly cookie，重設時保留） |

**為什麼新增一個原因代碼，而不是重用 `ACTIVITY_RESET`**：學生的 session 資料列在重設時就被刪除了，
重連時伺服器**分不出**這張 session 是被「重設」還是被「老師刪掉該組別」作廢的（兩種情況的資料庫狀態一樣）。
若重用 `ACTIVITY_RESET`，老師刪掉某組時、離線中的學生重連會看到「活動已重設」—— 那是錯的。
所以我們用一個中性的原因「進場狀態已失效」。

（若你們希望**重設**的情況就顯示「活動已重設」，我們可以改成保留一份作廢紀錄（多存一個「作廢原因」）→ 這是可行的，只是要多一點工作，我們可以配合。）

## 三、想跟你們確認的（契約要補一句）

### 提議的 D19 補充條文

> 現有（v0.10，Confirmed）：
> 「學生的 token 立即失效，**已連線的學生也會被通知（`session:invalid`，原因為「活動已重設」）並回到選組頁**（組別保留，重新點一下即可進場）」
>
> 提議追加：
> 「**重設當下不在線的學生，在重新連線時也會收到通知並回到選組頁**（原因說明為「進場狀態已失效」；失效原因在 session 被作廢後已無法分辨）」

### 想請你們回覆的三點

1. **同意**把 D19 的通知範圍擴到「重設當下不在線、之後重新連線」的學生嗎？
2. 你們那邊的學生端**沒有 token**（每次送出都重新檢查進場狀態），所以離線中的學生重連後、
   下一次送出時才會被擋回選組頁。**你們那邊也會在重連當下就跳回選組頁並說明原因嗎？**
   如果會，我們希望兩邊文案一致（我們目前是「進場狀態已失效，請重新選擇組別」／英
   "Your session has expired, please choose your group again"）；如果你們偏好直接寫
   「活動已重設，請重新選擇組別」，我們也可以配合（需多存一份作廢原因，見上一節）。
3. 原因代碼的名稱要不要對齊？我們新增的是 `SESSION_EXPIRED`；如果你們的 session 生命週期裡
   已有對應的代碼或錯誤名稱，我們可以統一。
