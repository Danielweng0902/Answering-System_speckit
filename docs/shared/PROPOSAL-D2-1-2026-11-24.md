## 一、要談的事：重設活動時，學生的登入狀態要不要一起清掉？

### 現況

| 項目             | 現況                                                                                    |
| ---------------- | --------------------------------------------------------------------------------------- |
| `sessions` 表    | 只有 `token_hash / role / group_id / created_at` —— **沒有 `expires_at`、沒有撤銷旗標** |
| 撤銷             | `revokeSession()` **只在老師按登出**時呼叫                                              |
| `activity:reset` | 只做 `clearAllAnswers()` ＋ `newSessionId()` → **舊的 student token 照樣有效**          |
| 重啟             | token 存在 SQLite 檔 → 伺服器重啟後仍有效                                               |

所以「重設活動」之後，**上一場的學生 token 仍然可以作答**（雖然作答資料已被清空）。
這是語意不一致：「重設 = 清掉這場、重新開始」，但登入狀態留著。

### 規格洞

`specs/001-activity-session/spec.md` FR-022：

> 重設後階段回到「準備中」，**組別保留，本次活動的其他資料清空**。

「本次活動的**其他資料**」有沒有包含**學生的登入狀態**？條文沒說。
契約表 D19 也只寫「本次活動的**作答資料**清空」。

→ 這就是我們要一起定的地方。兩種讀法都合理，但行為不同，所以需要共識。

### 我們的提議（方案 C）

**重設活動時，一併作廢該活動所有學生的 session（token 立即失效）。**

理由與影響：

| 項目                       | 說明                                                                                                                                                                                          |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **成本**                   | `sessionRepo.deleteSessionsByRole(database, 'student')` **這個函式已經存在**（2026-11-22 D18 時為了「重啟後老師須重新登入」而加的）。在 `activity:reset` 的 transaction 裡加一行即可，約 3 行 |
| **不會踢掉正在連線的學生** | socket 的身分在 `connection` 時解析一次就存在 socket 資料裡，**每個指令不重查 sessions 表**。所以重設當下，已連線的學生不受影響                                                               |
| **受影響的只有一種情況**   | 重設**之後**才連線、或斷線重連的學生 → 他們會變成 guest，回到「選組畫面」重新進場拿新 token                                                                                                   |
| **為什麼這是合理的**       | 重設本來就是「清掉這場、重新開始」：作答已清空、學生本來就要重答。讓他們帶著舊 token 繼續，反而可能出現「以為自己還在上一場」的狀態                                                           |
| **重設的時機**             | 只允許在「已結束」階段重設（FR-022）。此時沒有正在進行的搶答，學生本來就處於等待下一場的狀態                                                                                                  |

### 我們**不**提議的做法（供你們參考）

- **加 TTL（token 過期時間）**：會讓學生在**課堂中途**被登出 → 重新進場、重新答卷。
  TTL 必須大於一堂課（50 分鐘），但逾時邊界怎麼處理（同學分鐘數不同、跨堂重用）是個大坑。
  我們認為風險比它解決的問題大。
- **完全不動**：目前的狀態是「重設 = 只清作答，token 留著」。

### 需要的裁決

1. **同意**嗎？不同意的话，你們那邊對「重設」的語意是什麼？
2. 若同意，我們會：
   - 在 `activity:reset` 的 transaction 裡作廢 student session（約 3 行 ＋ 測試）
   - 更新 `specs/001-activity-session/spec.md` FR-022 與 AC-001-27，把「重設後舊的學生登入狀態失效」寫進條文
   - 更新契約表 D19
   - 補學生端的驗收：重設後重新連線的學生會回到選組畫面

## 二、我們自己決定了、不用你們介入的三項

這三項我們逐項讀了程式碼，結論是「現況已有足夠防護」或「危害不可忽略地小」，
列出來是為了讓你們知道**我們刻意不做**，不是忘記了。

### D2-4 答案陣列長度上限 —— 不做

我們先前在內部待辦裡把它寫成「一題可以送幾千個空格組合沒有上限」，**那個描述不準確**，
實際查證後有**三道防護**：

1. Engine.IO 封包上限 1 MB（`engine.io/build/server.js` 的 `maxHttpBufferSize: 1e6`）
2. `answerCommands.ts`：`answers.length !== question.blanks.length` → 回 `BLANK_COUNT_MISMATCH`
3. `validateAnswer`：單格 ≤ 200 code point

殘餘風險只有 zod 解析階段（1 MB JSON 最多約 35 萬個空字串 → 約幾 MB 記憶體 → 隨即被 ② 擋下）。
再加一層 zod 上限要新增錯誤代碼 → 動契約，收益不成比例。

### D2-5 同時在途的總記憶體 —— 不做

匯入路由已先驗老師身分（未授權不讀 body）、單檔上限 5 MB。
實測 20 條並發 5 MB 上傳讓 RSS 121→278 MB，但**只有認證過的老師能觸發**（要自己開 20 個分頁同時上傳）——
是自己搞自己，不是外部攻擊。替代方案（併發上限要新增錯誤代碼、降單檔上限要動 FR-003 的「不超過 5 MB」）成本都不划算。

### C1 合法登入讓 session 表無限成長 —— 不做

登入速率限制只計失敗（10 次/60 秒），但成功登入是**人工操作**，成長速率是人類手指的速度；
且老師 session 在伺服器重啟時就會被清。實質危害可忽略。

## 三、順便一提：另一件事我們已經自己解決了

你們那邊的 `REPLY-2026-11-23.md` 提到 cookie 屬性要統一成 `SameSite=Strict`，
我們已經照著改了（PR #28，2026-11-23 合併進 main）：
登入 `HttpOnly; SameSite=Strict; Path=/`（工作階段 cookie，不設 Max-Age）、登出時以 `Max-Age=0` 清除。
