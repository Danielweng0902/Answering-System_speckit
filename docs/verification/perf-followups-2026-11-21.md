## C. 產品面未保護的面向（**會改變行為，需先決定**）

GLM 讀程式碼確認的現況（`server/src/infra/http/authRoutes.ts`、`server/src/infra/http/app.ts`、
`server/src/infra/http/questionRoutes.ts`、`shared/src/schemas.ts`、`server/src/index.ts`）：

**已有的防護**

- 登入速率限制：10 次失敗／60 秒，只計失敗、成功登入**不清除**，依 `request.ip`
- `express.json` 預設 100 KB；匯入 raw body 5 MB ＋ 解壓後 50 MiB
- Engine.IO `maxHttpBufferSize` 1 MB；單格答案 200 code point

**未被保護的面向**

1. **合法登入沒有上限**：每次登入都新增一筆 session，session 表可無限成長
2. **`/api/student/join` 完全沒有節流也沒有認證**：每個請求 INSERT 一筆 session（壓測工具的 join 情境就是示範）
3. **連線數與指令頻率沒有上限**：連線數只受 OS 限制
4. **`answers` 陣列在 zod 層沒有長度上限**（單格 200 字有，但一題可以送幾千個空格組合沒有上限）
5. **單請求大小限制管不住同時在途的總記憶體**
6. **速率限制的 Map 沒有上限**（每個來源一個 entry，沒有總數上限）

**要不要做？** 這幾項都會改變系統行為（例如限制 join 會影響「同一教室大量學生同時進場」），
依專案規則需要先與另一小組（OpenSpec 組）確認，且要先決定門檻。
建議排在期末專題之後，作為「部署前的硬化（hardening）」工作。

| 決策       | 選項                                                                                                                                                  |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| C 是否要做 | ✅ **已做（2026-11-22）**：做 2 與 3，1、4、6 先做觀測不擋。詳見下節「C 的實作結果」                                                                  |
| 門檻由誰定 | ✅ **已定**：依「50 組班級 ≈ 200 人、且雲端部署全班共用同一個對外 IP」推導——爆發額度 600（≫ 200 人）、持續速率 30／分、連線上限 500。可用環境變數調整 |

## F. 冷啟瓶頸定位（codex/gpt-6.2-astra）｜2026-11-21

完整報告：[`perf-coldstart-audit-2026-11-21.md`](./perf-coldstart-audit-2026-11-21.md)。

**關鍵修正了先前的理解**：3.5 秒**不是「處理慢」，而是「排隊」**——以實際 ACK 到達時間排序的第 95 百分位那筆，共 5254 ms，
其中 **5172 ms 花在 handler 入口之前**，自身只處理 11 ms、回程 70 ms。所以要做的是**減少每輪廣播的總工作量**。

| 發現                               | 數字                                                                                                       |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 每筆作答只替老師與送出組重建快照   | 50 筆作答 = 50 份老師 + 50 份學生快照，同步廣播合計 **141.6 ms**（JSON 11.6 ms、結算 1.8 ms）              |
| **老師看板每次廣播都全場重讀作答** | 第一輪最後 50 筆廣播耗時 **654.2 ms**，其中 `listAllSubmissions` 占 **350.9 ms（53.6%）** → 排隊就這樣累積 |
| 老師 state 封包大小                | 最大約 **317 KB**（50 組 × 20 題的完整看板）→ 50 筆作答就是 15 MB 的寫入量                                 |
| RSS +45.8%                         | **重跑無法重現（-57.3%）** → 證據不足以歸因；V8 heap 容量 122 MiB、實用 24.7 MiB、配置器碎片 15.6→38.8 MiB |
| 送達逾時                           | 是**配對逾時**；多等 3 秒後 8,550 包的筆數與 revision 順序全部吻合（資料沒掉，是送達太慢）                 |

**修正方向（依效益）**：P1 老師看板增量更新作答索引（省 246–316 ms／50 筆）→ P2 同輪廣播共用快照 → P3 必要時合併老師看板廣播（但要維持「2 秒內更新」的契約）。

**驗收**：WS 與 polling 各跑 **5 次**，要求 ACK p95 ≤ 1 秒、三路必要 state 逾時 0、投影收到作答事件 0、RSS 增幅 < 20%、每秒 CPU p95 < 80%。

其他指標：越權／錯誤順位 **0** ✓；**必要 state 漏送** WS 冷啟 121、polling 冷啟 3366 ✗；
CPU 穩態 WS 68.6%／每秒 p95 **105%**（超過一個核心）✗；停止負載 60 秒後 RSS 增幅 WS **+45.8%**／polling **+82.4%** ✗。

### 結論與下一步（下一輪效能工作的依據）

1. **冷啟是最大瓶頸**：50 組在同一秒搶答第一題時 ACK p95 3.5 秒 =「倒數一開始、全班同時送出」的畫面 → 課堂上會真實發生。
   嫌疑：每個連線各自重建快照並序列化（先前刻意沒做的 **A5 同輪廣播共用快照**）＋ 每次廣播都重算結算。
2. **Polling 明顯更差**：升級式連線在冷啟時逾時 42% → 建議正式環境強制 `transports: ['websocket']`。
3. **記憶體不回落**：停止負載後 RSS 仍增加 45～82%（我另跑小規模測試甚至 +124%）→ 需要查（sessions 表？V8 heap 未回收？監聽累積？）。
4. **必要 state 漏送**：冷啟 WS 漏 121 筆 → 與「快照一次送太多、事件迴圈塞滿」一致，與 (1) 同源。

> 上述數字是**單機 loopback、每種負載只跑一趟**（審計要求至少 3 次），只能當方向性參考；
> 正式容量數字要等修正後重測並以 3 次以上取中位數。

### D0. 已由我獨立重現確認：**未認證冒名作答全鏈**（阻擋級，但屬設計使然）

實測（正式 build 的伺服器，本機）：

```
① 老師匯入題目、建立組別、開啟搶答
② guest 快照的 groups = [{"id":"500bd83a-…","name":"第一組"}]   ← 完全不帶 token 就拿到全部組別
③ POST /api/student/join（無認證）= 200、拿到 student token
④ 冒名 answer:submit → ack {"ok":true}                        ← 冒名作答被接受
```

**為什麼會這樣**：學生必須看得到組別清單才能選組（001 AC-001-09），所以 guest 快照本來就包含
全部組別的 id 與名稱；而 `student/join` 依規格就是免認證（AC-001-09）。
**跨組隔離本身有守住**（第一組看不到第二組的作答）。

**後果**：在 perimeter（VPN／內網）已被繞過的情況下，任何人都能免認證進入任意組、
冒名送出答案，污染老師的看板與結果。跨組別「偷看」則守得住。

**這需要兩組做產品決策**，不是純技術修正。可選方向：

| 方向                                   | 影響                                                      |
| -------------------------------------- | --------------------------------------------------------- |
| 維持現狀                               | 課堂內信任同學；perimeter 被繞過時可冒名                  |
| 每組加「加入碼」（4–6 碼，教師端顯示） | 擋住冒名，但**改變 001 AC-001-09 的學生端流程**（多一步） |
| 老師端能「鎖住某組」                   | 不影響學生流程，但只能事後防禦                            |
| 只在部署時限制來源網段                 | 需知道教室網段，環境相依                                  |
