# 壓測實測：100 組 × 20 題（2026-11-22）

> 目的：D20（組數上限）統一為 100 組之前，先用我們自己的壓測工具量一次 100 組的規模，
> 確認「倒數歸零、全班同時送出」的最壞情況不會壞掉。
> 工具：`e2e/load/`（`npm run build` 後跑正式 build 的 `server/dist/index.js`）。
> 原始 JSON：`docs/verification/load-test-2026-11-22/`。

## 環境與方法

| 項目 | 內容 |
|---|---|
| 機器 | macOS（Apple Silicon，本機單機，loopback） |
| Node | v26.7.0 |
| 伺服器 | `npm run build` 的正式 build，`TEACHER_PASSWORD` 由工具的環境變數提供 |
| Transport | WebSocket（`--transport websocket`；polling 另有量測） |
| 負載 | `--groups 100 --questions 20 --rounds 2` ＝ 100 組 × 20 題 × 2 輪 ＝ **4,000 筆合法作答** |
| 連線 | 100 組 × 2 條（送出者＋同組觀察者）＋老師＋投影 ＝ 202 條 Socket.IO 連線 |
| 統計口徑 | 全部樣本；逾時以 5,000 ms 當延遲下界（`docs/verification/perf-followups-2026-11-21.md` 的同一口徑） |

「冷啟搶答」情境是**最壞情況**：100 組在同一個時間窗內送出第 1 題的答案，
每一筆作答都會觸發一次作答廣播。

## 結果一：先做廣播合併之前（100 組，冷啟）

| 指標 | 數值 |
|---|---|
| 送出→ACK | p50 **1,592.75 ms**、p95 **5,000 ms**（逾時）、逾時率 **12.15%** |
| 老師看板更新 | p50 **2,601.59 ms**、逾時率 **38.90%** |
| 必要 state 漏送 | **2,528** 筆 |
| 錯誤順位 | **7** 筆 |

**原因**：老師看板是全場快照，100 組 × 20 題時每份約 600 KB；舊做法是**每筆作答都重建並
送出整份看板**，一輪 4,000 筆作答就是 2.4 GB 的序列化與寫入，事件迴圈被塞滿，
連學生的 ACK 都排在後面。

## 修正：老師看板的廣播合併（2026-11-22）

同一個時間窗（`TEACHER_BOARD_COALESCE_MS` ＝ 120 ms）內只送**一份最新看板**給老師，
學生自己的快照與 ACK 仍立即送出。120 ms 遠小於契約要求的「2 秒內更新看板」，行為不變。

實作：`server/src/infra/socket/broadcaster.ts`（`scheduleTeacherBoard()`／`flushTeacherBoard()`）。

> 「投影」欄位在所有情境都是 100% 逾時，這是**預期**：2026-11-21 起作答事件不再推給投影
> 連線（否則會用 revision 洩漏全場作答次數與時機），所以投影不會收到作答相關的 state。

## 結論

1. **100 組可用**：倒數歸零全班同時送出的最壞情況，ACK p95 158 ms、逾時 0%、
   漏送 0、錯誤順位 0，與 50 組同一個量級。
2. **廣播合併是關鍵**：若不做合併，100 組的冷啟會有 12% 的作答逾時（見結果一）。
   合併後老師仍看得到順位（p95 179 ms，遠小於契約的 2 秒）。
3. **CPU 是下一個天花板**：100 組的穩態 CPU 已到 61%，每秒 CPU p95 仍會超過單一核心
   （107.9%）；這是本機單機的數字，正式環境若用一般雲端主機建議同樣實測一次。
4. **部署門檻同步調高**：`JOIN_RATE_LIMIT_BURST` 600→1000、`MAX_CONNECTIONS` 500→1000
   （100 組班級約 400 人）。
