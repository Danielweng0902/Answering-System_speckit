# 2026-11-21 負載實測報告

> 本報告只採用最新版壓測工具產生的一趟中等 Socket.IO、一趟 HTTP、以及短階段煙霧測試。重複執行不足的項目不等同通過長期基準；未達標項目一律寫「未達標」。

## 1. 結論

- **HTTP 三情境全部達標**（10／25／50 req/s，真實 Socket.IO 作答洪流下的 health-full-room 也達標）。
- **WebSocket 中等提交的延遲門檻未達標**：ACK p95 3528.92 ms／p99 4095.07 ms；四路必要 state p95 3795.98 ms／p99 5000 ms。
- **polling 中等提交明顯未達標**：ACK p95／p99 都是逾時上限 5000 ms，逾時率 42.90%；四路 state 逾時 42.08%，漏送 3366。
- 兩種 transport 的**越權與錯誤順位都是 0**；公開輸出的三個 JSON 也不含密碼、token 或 Authorization。
- CPU 依「每秒樣本 p95 < 80%」判定：**未達標**（WS 105.00%、polling 103.80%）。穩態平均值供對照，不拿模糊的 `ps` 一生平均做結論。
- 停止負載 60 秒後 RSS 增幅 **45.81%（WS）／82.42%（polling）**，都超過 20% 門檻。
- 每種中等 transport 只有一次獨立啟動，因此延遲榜只能作當日的一輪工程訊號，不能宣稱穩定。短煙霧測試每個 transport 也只作可繼續性驗證。

### 5.3 關鍵實作差異

- 把 「1,000 筆種子」視為 **setup**，不是正式 transport 量測。其餘六種情境都使用本輪 transport 進行正式數據。
- `seedSetupTransport: websocket` 寫在 JSON。目的是避免 polling 的 setup 廣播積壓污染量測，種子期間量測用 teacher／projector 也暫時停線。
- 50 組重連是**依序發送**，不是同刻一次連上；這避免 presence 廣播形成自我疊加的 50×50 啟動風暴，但延遲仍逐條量。
- 老師／投影在種子結束後以乾淨佇列重接；不會把 1,000 個 setup 廣播當成自始自終的 answer→state 樣本。

## 7. 目前仍不可信或不能過度外推的地方

1. **重複性不足**：中等 Socket 每種 transport 只有一趟產生「最終版」結果。p95/p99 可能受當刻記憶體、IO 與 OS scheduler 影響，不能當長期基準。
2. **負載機與伺服器同機**：loopback 仍可展現 event-loop 問題，但沒有量到教室 LAN/Wi-Fi。
3. **Polling 的正式量測仍受 presence 規模影響**：依序重連比同刻同時開 50 條保守，但多角色 socket 仍在同一 event loop 內排隊。
4. **種子 setup 用 WebSocket**：這是明確宣告的 setup 差異，polling 的正式冷啟資料不應解讀為「純 polling 到處都是同速」。
5. **每秒 CPU 上限需要看 p95 不是平均值**：花了一段時間暖身與冷卻，平均值會把空轉稀釋掉，`ps time=` 也只有累計 CPU；同機負載工具仍會與 server 搶 CPU。
6. **HTTP 的 50 名是工具定義下的一步**：比上一版「只有 join 冒充」真，但還沒有做到 200 人長時間 peak。
7. **HTTPS attach 沒有真正對外跑過**：已驗證會改用 `node:https`／`https.Agent`，但沒有真實遠端伺服器執行；這一輪沒有把密碼送出本機。
8. **SIGKILL 仍不可能即時捕捉**：已由 PID owner＋30 分鐘逾時補救，但這不是原子清潔；`kill -9` 當下仍可能留下非常短暫的單一量測子程序。
