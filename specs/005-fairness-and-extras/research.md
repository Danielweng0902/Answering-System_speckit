# Research: 公平順位與投影看板（005）

**Branch**: `005-fairness-and-extras`｜**日期**：2026-11-17｜**對應**：[spec.md](./spec.md)

本文只記錄 005 新增部分的技术決策與其依據；技術架構沿用 [001 research](../001-activity-session/research.md)、[002 research](../002-guided-notes-import/research.md) 與 [003 research](../003-buzz-in/research.md)。所有實驗都由主控實際執行，腳本放在本機暫存區（不進版控），輸出如實抄錄。

## R1：公平順位判定採「衍生計算」，不新增判定結果的保存

**Decision**：判定（哪一組是某題的搶答成功組、各組的順位）**不存進資料庫**，而是由已保存的 `submissions.received_at`、`submissions.rank`、`voided_at` 每次即時推導。推導規則是純函式 `settleAll(questions)`。

**Rationale**：
- FR-009／SC-003 要求「只依據系統保存的送達時間與順序，重算 100 次結果 100% 相同」；衍生計算天生滿足，不需要額外的保存與一致性維護。
- Edge case「系統在某題的 3 秒內重新啟動，重啟後結果與沒有重啟時相同」：衍生計算不需要任何重啟恢復邏輯。
- **D25（2026-11-17 兩組同意）的連鎖重算在衍生計算下是自然結果**：作廢只是把該筆作答排除，重新推導時成功題數會跟著變化，後面已判定的題目自動重算。若把判定結果存成資料表，就得多設計「哪些判定要失效、何時重算、舊結果怎麼清掉」的一整套狀態機。
- 003 既有程式把 `decideWinner()` 當成唯一入口；005 只替換「順位如何排」的規則，資料保存、投影與廣播都不需要改動。

**實驗**（`settleAll` 的純函式版本，模擬送達資料）：

| 實驗 | 結果 |
|---|---|
| 1. 6 組 × 6 題同速作答 | 各組成功題數 `G1..G6` 各 1 題，**最多 − 最少 = 0**（SC-001 要求 ≤ 1）；每題勝出依序 G1、G2、…、G6 |
| 2. 同一輸入重算 100 次 | 結果 **100% 相同**（SC-003） |
| 3. 作廢連鎖重算（D25） | 作廢前 `1:G1 2:G2 3:G1`（成功 G1=2、G2=1）；作廢 G1 第 1 題後 → `1:G2 2:G1 3:G1`（成功 G1=2、G2=1）。第 2 題因 G1 成功題數歸零而改判，第 3 題在平手時依送達先後 |
| 4. 批次邊界 | 與第一個答案相差 **3000ms 算同一批**、3001ms 不同批；同批順位 `G1=1, G2=2`，不同批者排第 3 |
| 5. 效能 50 組 × 30 題 | 每次全場判定 **2.38 ms**（100 次平均） |

**代價與界線**：每次產生看板／結果／匯出都要重算一次判定；實驗 5 顯示這在上限規模下可忽略。`submissions.rank`（資料庫內的送達序號）維持原本語意，只作為送達先後的比較依據；**對外顯示的順位**改由判定結果提供（FR-021）。

## R2：批次定義為「相對於該題第一個答案的 3 秒窗」，每題只有一批

**Decision**：某題的「同一批」= 該題**第一個有效作答**送達後 **3000ms（含邊界）**之內送達的所有有效作答。超過 3 秒才送達的作答不屬於任何批次，依送達先後排在該批之後。

**Rationale**：
- FR-003 的原文就是「某題第一個答案送達後 3 秒內送達的所有作答視為同一批」，以第一個答案為基準只有一個批次；FR-005 明確規定「不屬於同一批的作答，順位排在同一批之後」。
- 一題只有一批，規則單純、可測；實驗 4 已驗證邊界。
- 判定時機因此明確：該題第一個答案送達後 3 秒（或活動結束時）即完成判定。

## R3：「判定中」是時間衍生的狀態，不需要排程器保存

**Decision**：某題是否「判定中」= `現在 < 第一個答案送達時間 + 3000ms`。這是純計算，不需要資料表、不需要背景工作。

**Rationale**：
- FR-010 只要求老師看板上把未完成判定的題目標示為判定中。
- 但「判定完成」的那一刻看板要從「判定中」翻成已判定，**只靠事件觸發的廣播不會自動翻**。因此仍需要一個**一次性的提醒**：某題第一個作答送達後 3 秒，由伺服器安排一次廣播（沿用 001 倒數計時器的排程手法）。這個排程只負責「提醒大家重新看一次」，不保存任何判定結果，伺服器重啟後最多只是少一次即時翻轉，下次廣播時狀態仍正確（R1 的衍生計算保證）。

## R4：公平順位下的「順位」是顯示層的順位，資料庫的 `rank` 維持送達序號

**Decision**：資料庫 `submissions.rank` 不變（仍是該題的送達序號，作廢後重送照舊排最後）；**顯示給老師與學生的順位**改由判定結果提供：啟用公平順位時是公平規則算出的順位，未啟用時與送達序號完全相同。

**Rationale**：
- FR-021 要求公平順位下學生端看到的自己組順位是公平順位。
- 保留資料庫欄位原義，可讓 003 的既有查詢、唯一索引與測試不必改動，降低跨子功能破壞風險（原則 I）。
- 未啟用公平順位時判定結果與 `submissions.rank` 相同 → FR-002／SC-002「與 003 完全一致」自動成立。

## R5：公平順位旗標與揭曉進度放在 `activity` 表

**Decision**：`activity` 表新增兩個欄位——`fair_ranking_enabled INTEGER NOT NULL DEFAULT 0`、`revealed_question_count INTEGER NOT NULL DEFAULT 0`，都用既有的 idempotent migration 方式加入（`migrateActivityColumns`）。

**Rationale**：
- 兩者都是「本場活動的設定／狀態」，與既有的 `countdown_ends_at`、`session_id`、`answer_event_count` 同一層級；不另開資料表（避免 004 那種「唯讀子功能不動 schema」的例外，也避免 schema 膨脹）。
- 旗標只有「準備中」可改，改動時 `activity.revision + 1` 並廣播，與既有 activity 指令一致。
- 揭曉進度放資料庫 → 重啟不遺失、重設活動時歸零（FR-023），且老師端與投影頁共用同一份真相（原則 VI）。

## R6：投影看板用「連線時的檢視模式」取得獨立快照，不重用老師快照

**Decision**：Socket.IO 握手帶 `view: 'projector'`；伺服器據此產生**獨立的投影快照**，內容只有階段、倒數、各組是否在線、是否啟用公平順位與已揭曉的結果。投影快照**完全不含**答案、送出狀態與送出數量。

**Rationale**：
- FR-015／C9／AC-005-14 要求搶答中投影看板不得顯示任何作答資訊；003 的做法是**在伺服器端過濾後才送出**（原則 VI），若讓投影頁拿老師快照再於前端隱藏，等於把作答資料送到瀏覽器，違反同一條原則。
- 身分仍是老師（AC-005-18：未登入不得使用），但「檢視模式」與「角色」是兩件事：老師頁需要看板，投影頁不需要。
- 揭曉動作由老師發出指令（`reveal:next` / `reveal:all`），廣播後投影頁依 `revealed_question_count` 只顯示已揭曉的題目。

## R7：CSV 第 8 欄的取值

**Decision**：第 8 欄名稱 `公平順位`，取值：`否`（本場未啟用）、`是`（已啟用）、`是（改判）`（已啟用，且該題的搶答成功者不是最先送達者）。Guided Notes 的 xlsx 不變。

**Rationale**：
- D13 v0.5 兩組同意「標在 CSV」，實作為第 8 欄；用一欄同時滿足 FR-011 的兩個要求（本場是否啟用、哪些題目因公平順位改判），避免擴到第 9 欄。
- 「改判」是老師最需要辨識的資訊：它代表這一題的結果不是因為手快。值用中文可讀字串，CSV 本身就有中文欄位，風格一致。

- 公平順位的批次長度 3 秒固定不可調（FR 與 D14 都如此），不提供設定。
